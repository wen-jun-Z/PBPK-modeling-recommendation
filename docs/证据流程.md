历史批次 `run_20260907T134918Z` 增加了已有药物的证据；`run_20260909T083120Z` 为20种新药入库1,144条证据，形成30药、2,872条证据的扩库基线。2026-10-26复核后，原30药有2,267条可用证据，新增70药有999条，共3,266条；待审项单列，不算可用证据。第1批修复完成，其余6批正在按相同规则处理。原批次验收与本次修复收据分别保留，以下旧批次路径与数量仅作为历史示例。

原文、最终证据、审核队列和数据库引用的解析文档保留。分块、解析表格与暂存状态可由原文重新生成；重新抽取应建立新处理批次，已完成 manifest 不表示所有中间文件仍在。

处理顺序：原始收集 → 解析与抽取 → 归属与去重 → 质量准入 → 索引与入库。全文保留四个阶段的科学规则和失败条件。

扩库必须明确传入药物清单，归属阶段读取本批次的收集计划，不使用固定旧药物列表。已有模型登记的药物沿用同一 ID；稳定身份字段冲突时阻止连接，不合并盐型或立体异构体。入库仅补齐未经人工审核记录的缺失身份字段，并保留来源和修改审计。新增证据覆盖数以实际可检索的准入证据为准，不以身份登记数或下载文件数代替。

DailyMed 标签即使返回 HTTP 200，也必须是有效 HL7 XML，且 `setId` 与请求一致。正文校验3次失败后，仅再尝试一次[官方固定版本 ZIP](https://dailymed.nlm.nih.gov/dailymed/app-support-web-services.cfm)，限32 MiB；核对成员路径、CRC、唯一主 XML、标签身份和版本后，按 ZIP 的真实地址登记。后备失败仍暂停。已有 `None` 响应仅在取回同身份、同版本归档后标为不可抽取的历史记录，原文件和失败解析结果保留，库存及解析重新验收；解析失败的文件不能作为其他文件的成功去重依据。

PMC 官方 XLS 若字节数、SHA-256 和官方单段 ETag 校验均一致，但 OLE 目录确定超出文件末尾，记录为“官方源内容损坏、未解析”的 `unsupported` 缺口，保留原件且不生成表格或证据。不能将本地下载不完整、来源不明或其他解析异常套用此规则。已核实缺口可单独重试并重新核验全批来源与统计；原失败记录保留，不重下已验收资料。

10月批次初次采集上限为每药100份PMC全文及25份开放包，但后续补全阶段也处理了初次暂缓项；初始清单不能作为最终未下载数量。2026-10-26逐文件核验的1,369个初次暂缓条目中，1,060个已有正文且已解析，304个只有摘要，5个只有元数据。下载成功、取得全文、完成解析和证据通过验证须分别统计；仅有摘要不算取得全文。新建普通采集任务仍使用代码默认的250份全文、100份开放包，不改写历史批次配置。

原扩库采用追加入库并检查原2,872条证据指纹；本次复核在隔离目录运行，只修订对应批次的已验证记录，其他批次与冻结实验保留。修复使用 `scripts/deployment/repair_expansion_quality.py watch` 查看进度。跟进程序 `scripts/deployment/follow_evidence_expansion.py quality-start` 每分钟核对该修复队列，每20分钟记录审计。仅在原文、提示词及完整服务回执确认是生成截断时，允许每批一次按原始片段和参数类别拆分恢复；不能拼接残缺JSON或清零失败计数。恢复失败、其他错误、手动暂停或磁盘异常均停止，状态在同一进度界面显示。

## 高精度原始资料检索策略

### 0. 三策略总顺序

```text
原始资料检索
  -> 原始资料解析与候选 evidence 抽取
  -> 最终 evidence 的化合物归属、领域门控、去重和冲突分析
  -> 最终证据层完成后再建立 RAG 检索索引
  -> 数据库、UI、Q&A 和导出
```

本文只执行第一阶段。输出是不可变 raw 文件和检索清单；不产生 parsed document、evidence、embedding 或数据库记录。

### 1. 目标

为每个目标化合物获取公开、可追溯且与 PBPK/PK 直接相关的原始资料。

本策略的完整性定义为：发现到的候选记录均有清单和处理决定；并不等于下载所有偶然出现药名的全文、标签或共享数据库文件。

本阶段只下载和保存原始文件及选择元数据，不抽取参数、不判断科学结论、不写 evidence。

### 2. 基本原则

1. 先发现候选，再决定下载。
2. 目标化合物必须可由名称或稳定标识符精确确认。
3. 文献全文、PMC 包、标签 XML 和试验详情只对高相关候选下载。
4. 未下载的候选不丢弃，保留元数据、原因和可重试状态。
5. 共享来源快照与化合物资料分开保存；共享快照默认不参与化合物运行。
6. API、PDF、XML、JSON、ZIP、CSV 等原始文件保持原样，`assets.jsonl` 只作为索引。

### 3. 化合物身份范围

每个化合物先写入身份查询清单，并保存以下来源的原始返回：

- 通用名和规范拼写；
- PubChem CID、InChIKey、RxCUI、ChEMBL ID、UNII（以来源实际返回为准）；
- 盐型、前药、代谢物、立体异构体；
- 商品名、制剂名、组合产品名。

`identity_coverage_manifest.json` 只记录身份发现使用的原始响应和缺失来源；它不是跨来源的 canonical identity 合并。每条候选资料必须标记一种关系：

| 标记 | 含义 | 是否可下载正文 |
|---|---|---|
| `exact_target` | 直接研究目标药物 | 可以 |
| `target_component` | 组合产品中明确研究该活性成分 | 需组件级确认 |
| `related_form` | 盐型、前药或代谢物 | 单独保存，不自动合并 |
| `mentioned_only` | 仅背景提及 | 不下载正文 |
| `other_component` | 组合产品的其他成分 | 不进入目标药物语料 |

### 4. 执行流程

```text
身份确认
  -> 候选 ID / 文件发现
  -> 结构化字段与标题摘要筛选
  -> fulltext_selected / metadata_only / excluded 分流
  -> 下载已选原始资料
  -> 写入资产、失败、覆盖和选择清单
```

每个产生候选记录列表的来源均产生：

- `candidate_records.jsonl`：发现的全部候选；
- `fulltext_selected_records.jsonl`：下载正文或详情的候选；
- `metadata_only_records.jsonl`：保留元数据、不下载正文的候选；
- `excluded_records.jsonl`：排除候选及原因。

这些选择文件是检索元数据，不是科学证据。

### 5. PubMed 与 PMC

#### 5.1 查询方法

文献查询必须同时满足：

```text
目标药物在 Title
AND
对应 PK / ADME / DDI / 特殊人群 / PBPK / 制剂主题在 Title
```

主题分组：

| 分组 | 查询词示例 |
|---|---|
| Clinical PK | pharmacokinetic, AUC, Cmax, Tmax, clearance, half-life, bioavailability |
| ADME | absorption, distribution, protein binding, metabolism, excretion, CYP, UGT, transporter |
| DDI | drug interaction, coadministration, inhibitor, inducer, victim drug, exposure |
| 特殊人群 | renal impairment, hepatic impairment, pediatric, pregnancy, lactation |
| PBPK | physiologically based pharmacokinetic, PBPK, PK-Sim, MoBi, Simcyp |
| 制剂/食物影响 | food effect, formulation, dissolution, permeability, modified release |

特殊人群和制剂/食物效应查询还必须在 Title/Abstract 有明确 PK 术语，例如 `pharmacokinetic`、`AUC`、`Cmax`、`clearance` 或 `bioavailability`。不使用仅含药名的宽泛全文检索，不把 MeSH、补充概念或仅在摘要中偶然出现的药名直接作为全文下载依据。

#### 5.2 文献分流

对每个命中的 PMID 以最多 100 条一批下载 ESummary 和 EFetch XML，并对失败批次重试，用标题和摘要进行规则筛选：

| 决定 | 条件 | 后续动作 |
|---|---|---|
| `fulltext_selected` | 目标药物和对应主题均在标题；并且有明确 PK/ADME/DDI/PBPK 术语，或特殊人群/制剂主题有摘要 PK 支持 | 解析 PMID 到 PMCID，下载 OA XML、PDF、补充材料 |
| `metadata_only` | 药物仅在摘要出现、主题不在标题、或角色/研究对象不明确 | 保留 PMID、DOI、摘要和原因，不下载全文 |
| `excluded` | 背景提及、食品/补充剂/植物内容、药物不是研究对象或主题不符 | 保留排除记录，不下载全文 |

例如“咖啡因灌肠促进毒性产物排泄”不应成为 caffeine `excretion` 的全文下载目标；“caffeine clearance in healthy volunteers”应进入全文队列。

边界记录可写入 `metadata_only`，后续由 LLM 仅根据标题、摘要和检索上下文做辅助分类。LLM 不读取全文来决定科学事实，也不生成 evidence。

#### 5.3 PMC、PDF 和附件

只对 `fulltext_selected` PMID 查询 `pubmed_pmc` 链接；每个 PMID 与 PMCID 映射必须可验证。

对开放获取文章下载：

- PMC EFetch XML；
- OA package 元数据；
- 官方提供的 NXML/XML、PDF、补充材料、表格和图片；
- 许可证和下载状态。

PMC ELink 和 PMC XML 以最多 20 条一批请求并重试；失败批次保留在 `failures.jsonl`，不得静默跳过。

无合法开放路径时仅保存 PMID、DOI、摘要、访问状态和原因。PMC 链接批次请求失败时，必须单列为“链接查询失败/待重试”，不得误标为“确认无开放全文”。不得抓取付费出版商全文。

`--max-pmc-fulltext-per-compound` 和 `--max-pmc-oa-packages-per-compound` 是运行保护阈值，不是相关性判断；设为 `0` 表示不设置数量上限。超过阈值时，按对应 PubMed 标题/摘要筛选分数排序，延后条目写入 gap manifest，不能静默丢弃。

### 6. 结构化来源规则

| 来源 | 发现与筛选 | 下载内容 |
|---|---|---|
| PubChem / RxNorm / ChEMBL | 用精确 CID、InChIKey、RxCUI、ChEMBL ID 核对；名称搜索只用于身份发现 | 原始 JSON、同义词、结构和属性记录 |
| DailyMed | 先取得 SPL 列表；仅目标药物精确出现在标题且默认不是组合产品的记录下载 XML | SPL 列表页、选中的 SPL XML、版本和 set ID |
| openFDA | 精确 generic name 查询；组合产品记录保留身份标记 | 原始标签 JSON 和版本信息 |
| PK-DB | `studies/?substance=<compound>` 精确研究列表；`filter/?studies__substance=<compound>&concise=false` 核对对象计数 | study detail；官方 `filter` 接口的 `download=true` ZIP；ZIP 内 group、individual、intervention、output、timecourse、scatter 与元数据 |
| ClinicalTrials.gov | 使用 `query.intr=<compound>` 与 PK 主题 `query.term` 发现候选，以 100 条安全分页；候选页只请求 NCT ID、标题、摘要和干预名称；仅目标药物为干预或 PK probe 且有 PK 主题的研究进入选中队列 | 候选页原始 JSON；仅对 `fulltext_selected` NCT 下载完整 study JSON |
| OSP 模型库 | 单独的共享仓库缓存；后续以模型文件名、说明和 compound metadata 选择目标模型 | PKML、参数、脚本、报告、版本信息 |

DailyMed 组合产品默认只保留 `metadata_only`。只有显式使用 `--include-combination-labels`，才会下载组合标签 XML；后续仍需验证文本是否确实讲目标成分。

PK-DB 必须按以下顺序采集：

1. 用 `studies/?substance=<compound>` 分页发现 study SID，并保存每个 study detail。
2. 用 `filter/?format=json&studies__substance=<compound>&concise=false` 保存全部可发现对象计数；另用增加 `studies__licence__in=open` 的请求保存可公开复用数据计数和导出 UUID。
3. 对同一 filter URL 增加 `download=true`，下载官方 ZIP 原件；保存 URL、时间、响应头、文件大小和 SHA-256。
4. 安全解压到不可变目录，拒绝绝对路径、`..`、符号链接、重复成员和超出限制的压缩包。
5. 逐文件记录成员路径、大小和 SHA-256；按各 CSV 的稳定主键统计唯一 study、group、individual、intervention、output、timecourse 和 scatter，并与同一 filter 请求的计数核对。
6. 列表或单对象 API 返回空/404 时，不得把已有的 filter 非零计数改写为“无数据”；使用官方 ZIP 作为 output/timecourse 的权威公开下载路径，并记录列表接口状态。
7. 若开放许可 ZIP 未提供观测表，可用 study detail 中的 reference PMID 经 NCBI ID Converter/ELink 验证 PMCID，并下载该原始论文的 PMC OA XML、PDF、图片、表格和补充材料。此路径只能从论文原件重新提取观测值；PK-DB 只作为研究发现来源，不能复制其 closed-licence curated values。

只有开放许可 ZIP 下载成功、唯一对象计数校验通过且 study identity 与目标化合物精确匹配时，PK-DB 的浓度-时间数据才可进入后续处理。HTTP 200 但 `outputs.csv` 或 `timecourses.csv` 为空时必须标成 `observation_tables_missing`，不得视为完整。ZIP 不可用时保留 study metadata，并把缺口标成 `official_bulk_export_unavailable`。

监控核验官方 URL、目标药物、ZIP 与审计 SHA-256，并确认差异仅为观测表为空后，将该项识别为 `source_gap_metadata_only`，继续其他药物与来源的下载。原失败记录、非零索引计数和缺口均保留；空导出不进入证据抽取。网络失败、内容损坏、其他计数异常及磁盘超限仍触发停止，不能自动忽略。

openFDA 精确通用名的首页查询若返回 404，须再次核验官方响应明确为 `NOT_FOUND / No matches found!`，保存响应原件、校验值及缺口记录后才可继续；该结果只说明本次名称查询未命中，不代表该药物不存在其他名称的标签。普通 404 页面、服务器错误和后续分页缺失仍需停止处理。

ChEMBL 名称查询遇到 500/502/503/504 时，仅在本批次 PubChem 精确名称、CID、InChIKey 和 RxNorm 查询原件完整且校验通过后，允许一次有超时及大小限制的复查。复查仍为服务端错误时，保存原始错误响应，将 ChEMBL 标为可重试的来源缺口并排除其响应，不推断该药物不存在；其他来源继续收集和处理。此规则不放宽后续身份、归属及证据质量门控，也不豁免内容损坏、身份不明确或其他来源的网络故障。

复查恢复 HTTP 200 时，须核验唯一精确名称、ChEMBL ID 和与 PubChem 一致的 InChIKey，再将响应原件登记为已恢复的身份资料，进入正常解析流程；不能继续按来源缺口处理，也不能把原始资料恢复当作证据已通过验证。

### 7. 共享来源快照

DrugCentral、HPA、GTEx、NHANES、AACT、EMA、OSP 等属于来源级资料库，不属于单个药物的直接语料。

```text
source_cache/<source>/<snapshot_id>/
  官方快照、仓库、版本、checksum

compound_runs/<run_id>/
  只保存该次筛选后的药物相关资料和选择清单
```

化合物运行默认不下载共享快照。共享资料必须同时传入 `--include-shared-sources` 和至少一个 `--shared-source <source_id>`，写入独立缓存和 `snapshot_manifest.json`；这样避免每次跑 10 个化合物都复制或扫描 HPA、NHANES、OSP 等整库。

### 8. 输出与可追溯性

正式 run 目录至少包含：

```text
RUN_STATUS.json
acquisition_plan.json
```

### 3.1 分阶段执行合同

每次命令只允许推进一个显式阶段：

```text
inventory -> parse -> deterministic_extract -> llm_extract -> table_recovery -> completeness
```

规则：

1. `inventory` 只生成清单和采集失败终态，不解析正文。
2. `parse` 只生成 parsed documents、parsed tables 和 text chunks。
3. `deterministic_extract` 只运行结构化 mapper 和规则抽取。
4. `llm_extract` 只处理分类为 `llm_required` 的 chunk。
5. `table_recovery` 只处理 `deferred_unparsed_flattened_table`，先复用现有 `parsed_tables`，再回到 raw 文件恢复缺失表格；不得重新调用正文 LLM。
6. `completeness` 在正文证据和表格证据完成后运行。
7. `completeness` 通过后本策略完成；`pipeline_state.embedding = not_started` 是预期状态，不是失败。
8. 每个阶段完成后更新 `pipeline_state.json`；后续阶段必须检查上游阶段已通过。
9. 不允许一次命令隐式跳过未通过的上游阶段。
10. 最终证据语义去重由最终证据策略执行；不得在这里预先对全部 chunk 做 embedding 来代替去重。

4. `repo`：OSP `.pksim5` 虽按模型仓库语义保留为 `repo`，实际用 SQLite 只读解析器提取 schema、非 BLOB 字段及 BLOB 的大小/checksum；不在本阶段复现模型。

7. `specialized_binary`：识别格式和版本。对 `.pzf` 使用支持 GraphPad Prism 的只读解析器；解析器不可用时写 `unsupported_specialized_format`，不生成 evidence，也不当作文件损坏。
8. `unknown`：Step 1 必须先尝试 magic 识别。当前正式语料不允许残留 `unknown`；后续新增格式必须先补策略与分类测试，再进入 parser 阶段。

本阶段执行顺序：

1. 按 `canonical_raw_asset_id` 合并 alias compound，生成每条 parsed 输入的 `retrieval_compounds`；别名只补检索上下文，不复制科学证据。
2. 对每条 `parsed_record` 运行 source-specific mapper：
   - PubChem：只读取 `PropertyTable.Properties` 的明确理化字段；
   - ChEMBL：只有 `pref_name` 或 synonym 与目标化合物规范化后完全相等时读取分子属性；
   - OSP 模型库：只读取仓库清单中目录名与目标化合物完全匹配的 `.pksim5` 文件；
   - DailyMed、RxNorm、PubMed、PMC、PK-DB、ClinicalTrials 和 OpenFDA 的身份、目录、试验上下文或检索元数据不伪装成七类 evidence；只写处理终态或 topic pointer。
3. 对每条 `parsed_table` 检查来源、列语义和 evidence signal。只有存在已批准的 source-specific 列映射时直接写 evidence；其他复杂表写 `deferred_complex_table`，供后续选择性 LLM 处理。
4. 对每条 `text_chunk` 先运行机器文本、搜索列表、长度、自然语言和 evidence signal 分类，再运行高精度 PK 数值规则、DDI 关系规则和 topic pointer 规则。截取 `source_text` 时，数字之间的小数点和 `e.g.`/`i.e.`/`vs.`/`et al.` 等常见缩写中的句点不得作为句子边界；证据片段必须保留完整参数值和必要对比语境。
5. PK 数值规则必须校验参数与单位类型；无可靠单位或明显属于数值数组、剂量、年份、编号的匹配不写 evidence。自然语言 PK 数值还必须命中明确的局部关系模板：`化合物 → PK 参数 → 数值+单位`、`PK 参数 of/for 化合物 → 数值+单位`，或等价的 `was/is/=/of` 紧密语法。目标化合物只是出现在同一句、数值属于另一药物/代谢物/对照组、参数后插入其他列名再出现数值，并列参数和并列数值无法一一对齐，或多药比较时当前数值的主语不明，均只写 `clinical_pk` pointer。`.pksim5`/MoBi/PK-Sim 内部命令、参数设置记录、`set from/to`、`assumed`、图表 `threshold`不是临床观测值，不得写为 clinical PK evidence。`creatinine clearance`/`CrCl`/`CLcr`/`CL cr`/`CL_CR`/`eGFR` 属于受试者肾功能条件，不得映射为药物 clearance。透析/血液透析清除率不得映射为常规 systemic clearance。`higher/lower/later/earlier/increased/decreased/reduced by N unit` 属于变化量，不得映射为绝对 PK 参数；这些结果只写 pointer。`under/over/about/approximately/≤/≥` 等限定词必须写入 `value_qualifier`，不能把边界值当作无条件精确值。
6. ADME、特殊人群和 PBPK 仅命中关键词但没有数值或关系断言时写 `evidence_pointers.jsonl`，不得写入 evidence。
7. 自然语言规则结果只有原文同一句明确命中唯一目标化合物，且该化合物与当前参数—数值或 DDI 关系存在明确局部关联时才写 evidence。DDI 还必须是明确、肯定、非否定的关系断言；`not/neither/whether or not/no evidence`、问句、`may/might/could/possibly`、以及 `parent drug and/or metabolites` 共同主语均只写 pointer。未命中目标化合物、多目标化合物、命中 `1′-OH`/`hydroxy`/`desmethyl`/`glucuronide` 等代谢物主语、PK 局部关联不明、DDI 多靶点或关系方向/极性不明确时，只写带原文的 `clinical_pk`/`ddi` pointer，并保留 `retrieval_compounds` 和 `compound_assignment_status` 交给后续 LLM。不得仅凭 retrieval compound 或同句共现断言证据归属。
8. 所有确定性 evidence 写入 `evidence_candidates_deterministic.jsonl`，并以相同内容初始化 `evidence_candidates.jsonl`；后续 LLM 阶段只在此基线上合并结果。


```text

compound_assignment_status
```


### 15. Step 11: LLM 辅助抽取

#### 15.1 LLM 调用前高精度路由

按以下顺序执行，任一步不通过即不调用 LLM，并在
`chunk_processing_status.jsonl` 记录原因：

1. **来源和章节准入**
   - DailyMed 只允许 Clinical Pharmacology、Pharmacokinetics、Absorption、Distribution、Metabolism、Excretion、Drug Interactions、Use in Specific Populations、Renal/Hepatic Impairment、Pediatric/Geriatric Use、Pregnancy、Lactation 等核心章节。
   - openFDA 只允许与上述章节对应的自由文本字段。
   - ClinicalTrials 的 brief summary、detailed description、eligibility 和研究计划只作为试验元数据；只有 results/outcome results 字段中的已发布 PK 结果可以进入 LLM。
   - 排除 Indications、Dosage/Dosing、Warnings、Adverse Reactions、Safety、Efficacy、Overdosage、Patient Counseling、References/Bibliography、Introduction/Background、Methods/Materials、Study Design、Objectives 和 Eligibility 等非结果内容。
   - OSP 模型报告只有原文明确出现 PBPK、physiologically based、whole-body、PK-Sim 或 Simcyp 时例外放行模型描述。
2. **文献层去重**
   - 从 `parsed_documents.metadata_json` 读取 PMID、PMCID 和 DOI。
   - 同一 PMCID 已有 PMC 全文时，不再把对应 PubMed 摘要送入 LLM；保留摘要记录和 `skipped_pubmed_abstract_with_pmc_fulltext` 状态。
3. **句级证据断言筛选**
   - 从 chunk 中提取保持原文字符不变的完整句子；最多合并相邻两句处理跨句参数结果。
   - 候选原文必须逐字出现唯一 `target_compound`，并包含 PK、ADME、DDI、特殊人群或 PBPK 参数/机制词。
   - PK 数值候选必须具有参数与数值/单位或明确升高、降低、延长、缩短等结果关系。
   - 定性 ADME/DDI 候选必须具有明确关系，例如 metabolized by、substrate of、inhibits、induces、transported by、excreted unchanged。
   - 特殊人群候选必须同时具有目标化合物、人群标志、PK/ADME 参数和差异关系。
   - PBPK 模型候选必须同时具有目标化合物、明确 PBPK 标志和模型建立、验证、预测或模拟关系。
   - 仅描述研究目的、计划测量、给药剂量、样本采集、疗效、安全性、镇静或不良反应的句子不进入 LLM。`regression/model/analysis ... to estimate/predict AUC/Cmax` 等参数估计方法也不作为已观察 evidence；明确 PBPK 模型建立语句除外。
   - `may/might/could/hypothesize/expected` 等不确定或预测性断言不进入 LLM；参数明确属于另一药物时，除非原文同时明确给出目标药物的 DDI 角色，否则不进入 LLM。
   - `not studied/not expected/unknown` 等未观察或否定证据、截断句、参考文献条目和仅有药效学终点的句子不进入 LLM。
   - 定性代谢/转运关系必须由局部语法明确连接目标化合物与 metabolized、substrate、inhibitor、inducer、transported、excreted 等关系词；组合制剂中另一活性成分的关系不得因邻近出现目标名称而放行。
   - 每个候选句必须独立通过否定、完整性和归属检查；否定句、参考文献标题或截断句不得与后一结果句合并后放行。
   - 当前句只提供目标药物语境时，只有后一结果句未再次明确目标药物才合并两句；后一结果句本身已形成完整目标药物断言时，只保留该结果句，禁止同时保留重叠的两句版本。
   - `PK/excretion/clearance/absorption ... of <其他物质>` 等局部所有者优先于检索目标；目标药物仅作为治疗、给药或研究背景时，不得把其他药物、内源性物质或代谢物的参数归给目标药物。只有原文明示 co-administration、presence of、effect of target on 等 DDI 角色时才可送入 LLM 判断。
   - `was/has been determined/evaluated/measured` 只说明做过测量，不是结果；没有参数数值、方向变化或明确机制关系时不进入 LLM。`different sites/groups/doses` 等研究设计修饰词不得被误当作 PK 差异结果。
   - 自然语言候选若括号未闭合、以逗号/冒号/连接词/`almost`/`Eq.` 等悬空成分结尾，或无终止标点且以 `Although/suggest that/approximately` 等从属片段开头，判定为截断。
   - 只有带 `parsed_table_id` 的完整表格行可进入 LLM。由 XML/JSON/标签正文展平、没有可靠行边界的表格片段写 `deferred_unparsed_flattened_table`，等待表格解析，不调用 LLM。除 `Table/§/‡` 等显式标志外，高数值密度且重复出现多个括号区间的文本也按展平表格识别。
   - `should be initiated/used/administered`、剂量调整、监测和禁忌等临床建议不是 PK/ADME 结果，不进入 LLM；同一 chunk 中其他独立结果句仍可保留。
   - PBPK 候选中的目标药物、PBPK 标志和 developed/validated/predicted/applies/describes 等模型关系必须位于同一局部断言；封面、URL、版本信息或远处的 `based on` 不得与标题拼接成模型证据。
   - `predicted/probably/likely` 等预测或推测关系默认不进入临床 PK/DDI 抽取；只有明确 PBPK 模型断言中的模型预测可以例外放行。
   - `creatinine clearance/CrCl/CLcr/eGFR` 是受试者肾功能指标，不作为目标药物 clearance；句子没有其他明确药物 PK/ADME 结果时不进入 LLM。
   - 以 `suggest that/indicate that` 开头且缺失前置主句的抽取残片直接判定为不完整，即使其后出现 PK 参数词也不放行。
4. **句级跨文件去重**
   - 对 `target_compound + 规范化候选句` 计算稳定指纹；规范化只用于比较，不修改送入 LLM 的原文。
   - 相同句优先保留 DailyMed 而不是 openFDA，优先保留 PMC 全文而不是 PubMed 摘要；同来源内按稳定 `source_location + chunk_id` 选择 canonical 句。
   - 非 canonical 句写 `skipped_duplicate_llm_sentence`，并记录 canonical chunk_id 和句指纹。
5. **调用单位**
   - 一个请求只包含同一 chunk 中通过筛选且由该 chunk 持有 canonical 归属的原文句子。
   - `llm_required` 只统计高精度路由完成后的请求候选，不再统计仅命中宽泛关键词的 chunk。
   - 全量调用前必须先运行 `classify-only`，输出来源分布、跳过原因、句级去重数、唯一请求数和随机样本。

LLM 输出校验：

1. 调用前必须确认 `inventory`、`parse`、`deterministic_extract` 均为 `completed + accepted`，且 `completeness`、`embedding` 尚未开始。
2. 每个请求必须有唯一 `target_compound`；无法从 chunk 或原文唯一解析目标化合物时不调用 LLM。
3. LLM 只能抽取明确属于 `target_compound` 的断言。对照药、合并用药、辅料、仅提及药物及关系方向不明确的多药文本不得归给目标化合物。
4. 每条候选必须通过 Pydantic schema，并返回与请求完全一致的 `target_compound`。
5. 必须有 `source_text` 和 `source_location`；验收后的 `source_text` 必须与当前请求中的某个完整 `input_items` 项逐字相等，并包含目标化合物名称。LLM 返回该项的任意精确子串时，无论子串是否已含目标药名，校验器只能在其唯一对应一个完整项时扩展为该项，并记录 `validation_repairs=expanded_source_text_to_complete_input_item`；无法唯一扩展时拒绝。禁止把完整句截成 `from the i.v.` 等仍可在 chunk 中定位的片段。
6. `source_location` 必须能回到 raw 文件；`checksum` 必须等于 raw inventory 中的 checksum。
7. `raw_asset_id`、`parsed_document_id`、`parsed_table_id` 或 `chunk_id` 必须能解析到上游记录。
8. 单值使用 `value`；范围使用 `value_low + value_high`，不得把范围写成字符串或擅自计算中点。返回的每个数值都必须出现在 `source_text`，且必须带单位；单位必须进入 canonical unit map。`less than/under/<`、`greater than/over/>`、`up to` 等边界必须写入 `value_qualifier`。定性候选必须使用 `value=null, value_low=null, value_high=null, unit=null, value_qualifier=null`。
9. `source_text` 必须形成完整断言。自然语言文本在 `from`、`to`、`between`、`and`、`by`、`in`、`after`、`before`、`when`、`while` 等连接词处结束，存在未闭合括号，或以未完成的条件、比较、伴随用药从句结束时必须拒绝。无句末标点的自然语言只在以完整数值/单位、明确 PK/ADME 谓语或完整酶/转运体关系结束时允许。只有 `parsed_table_id` 指向的完整表格行可免除句末标点要求；未解析展平表格不得写 evidence。调用前分流与调用后校验必须复用同一完整性判定。
10. `evidence_type + parameter` 必须符合计划第 6.2–6.7 节：`clinical_pk` 只允许 PK 参数；`special_population` 只允许特殊人群 PK/ADME 差异；`ddi` 只允许暴露/PK 变化或酶和转运体机制；`adme`、`physicochemical`、`tissue_expression`、`public_pbpk_model` 分别使用本域参数。
11. 参数名必须由 `source_text` 的术语支持：例如 `Cmax` 必须出现 Cmax/maximum/peak concentration，`steady_state_concentration` 必须出现 steady-state concentration，AUC/Tmax/half-life/clearance/volume 等同理。
12. 原文出现直接百分比变化，例如 `56% reduction`，唯一边界百分比，例如 `less than 0.5%`，或明确 `2.5-fold` 变化时，候选不得把对应 `value` 和 `unit` 留空。若 LLM 漏填，校验器可逐字复制唯一数值及 `%`/`fold`；边界表达还必须写 `value_qualifier`。分别记录 `direct_percent_change_from_source_text`、`bounded_percent_from_source_text` 或 `direct_fold_change_from_source_text`，不得计算比例或把剂量、样本量当作 PK 结果。
13. 含 `x vs y`、`x versus y`、`respectively` 成对数值或其他两个数值直接比较的原文，不把任一标量自动归给某个人群/处理组；数值候选拒绝，定性候选可保留整句供专用 LLM 复核，仍无法解析时隔离。
14. `increased/decreased/reduced by 60%` 等变化词在数值前的表达与 `56% reduction` 同样按唯一原文百分比提取；若候选给出的百分比与该直接变化值不一致则拒绝。
15. 参数与数值单位维度必须一致：Cmax/浓度使用浓度单位，AUC 使用 AUC 单位，Tmax/half-life 使用时间单位，clearance 使用清除率单位，volume 使用体积单位；百分比变化和 ratio 可用于相应参数的相对变化。
16. `dialysis/hemodialysis/dialyzable` 清除率和 `creatinine clearance/CrCl/eGFR` 肾功能指标不得写成目标药物的系统清除率；只保留原文审计。
17. compound 文献中的受体/蛋白染色变化不得写为 `tissue_expression`；Stage 1 tissue expression 由 HPA 等结构化表达来源处理，LLM 不生成该类型。
18. `public_pbpk_model` 原文必须明确出现 PBPK、physiologically based、whole-body、PK-Sim 或 Simcyp 等 PBPK 标识；普通 population PK/PD、经验模型或仅写 `model` 的文本拒绝。
19. `special_population` 的 renal/hepatic impairment、pediatric、elderly、pregnancy、obesity、pharmacogenomic、alcoholic/chronic alcohol use 等人群标志必须逐字出现在 `source_text`；LLM 生成的 `condition` 不能单独证明特殊人群归类。
20. 镇静、呼吸抑制、疗效、安全结局、适应证和单纯剂量/给药建议不得伪装成 PBPK evidence；只写审计拒绝记录。
21. `target_compound and its metabolite`、`target_compound and hydroxy/desmethyl/glucuronide metabolite` 等共同主语的参数不得归给父药；必须拒绝并保留审计。联合主语检查仅作用于包含当前候选参数的句子；同一连续引用项中的其他独立句若明确只描述父药参数，可单独通过。
22. 同文复用键必须由 `target_compound + input_text_or_table` 共同计算；不同化合物之间禁止复用 LLM 结果。
23. 校验失败写 `processing_failures.jsonl`，并记录稳定 failure_id、request_id、candidate_index 和失败原因。
24. 校验通过写 `evidence_candidates_llm.jsonl`，再按稳定 evidence_id 合并到 `evidence_candidates.jsonl`。
25. 所有 LLM 结果仍为 `needs_review`，不得自动进入人工通过层。
26. 先运行 10 个真实请求的冒烟批次；逐条核查所有通过和拒绝候选，仅当 API、schema、化合物归属、跨句引用、文本完整性、父药/代谢物边界、参数域、数值限定符和单位校验通过时才启动全量批次。全量运行期间持续抽样新写入的通过候选，并用确定性完整性检查扫描；发现通过候选含截断原文时立即停止、归档并修复，不把中止批次并入正式结果。
27. 全量批次可断点续跑：已有成功 request_id 不重调；同一目标化合物的相同 input_hash 可复用；运行中持续写请求、响应和进度审计。
28. 只有全部可处理 chunk 已成功、复用或明确跳过，且没有未解决失败时，才将 `pipeline_state.stages.llm_extract` 写为 `completed + accepted`；受请求上限限制的冒烟批次保持 `in_progress`。路由升级后不再满足调用条件的旧 API 失败必须保留原审计行，并更新为 `resolved=true, resolution=no_longer_eligible_under_current_routing`，不得删除或继续盲目重试。
29. 混合时间单位的范围仅在原文中唯一、明确绑定当前参数且两端换算均可验证时接受统一单位，并记录换算校验标记；不得放宽剂量、其他参数或组间对比的数值归属。百分比区间连接号与负号须区分。软连字符差异仅允许唯一匹配后恢复完整原始引用，不改写来源文件。复用响应必须同时匹配提示词和校验器版本。

### 15A. Step 11A: 延后表格恢复与证据抽取

输入：

```text
chunk_processing_status.jsonl 中 processing_status=deferred_unparsed_flattened_table 的行
parsed_tables.jsonl
raw_inventory.jsonl
原始 raw 文件
```

执行顺序：

1. 按 `raw_asset_id` 汇总延后 chunk；每个 chunk 只允许一个终态。
2. 扫描 `parsed_tables.jsonl`，优先复用同一 raw asset 已存在的表格：
   - DailyMed 按 `section[n]` 对齐 chunk 与 table；
   - PDF 按页码对齐；
   - PMC 按 article/table-wrap、PMCID 和 source location 对齐；
   - 其他来源至少按 `raw_asset_id + table_hash` 对齐。
3. 对已有表格展开完整行，写 `recovered_table_rows.jsonl`；不得重新写入同一 `parsed_table_id + row_index`。
4. 只有 raw asset 没有可用表格或现有表格无法覆盖延后位置时才回到 raw：
   - DailyMed SPL XML：读取 `section/text/table/tr/th/td`，展开 `rowspan`、`colspan`，保留章节标题、caption 和 footnote；
   - PMC JATS XML：读取 `table-wrap`、caption、label、thead/tbody/tr/th/td、fn，展开跨行跨列；
   - HTML：按 DOM table 读取 caption、thead/tbody/tfoot、行列和单元格；
   - PDF：按页使用文字坐标和表格检测恢复行列，保留页码和 bounding box；扫描页只写 `ocr_required`，不把 OCR 猜测当成证据；
   - CSV/TSV/XLS/XLSX/SQLite/PK-DB：读取明确列和完整行，不把展平正文当成表格；
   - 压缩包：只读取已登记 archive member，保持 `<archive>!<inner_path>`，不重复处理 checksum 相同的成员；
   - OpenFDA：从 JSON result 读取 `set_id`/SPL 标识并链接到已下载 DailyMed SPL；同一标签只保留 DailyMed 为 canonical table source；
   - PubMed 摘要没有表格正文时写 `not_table_in_abstract`，不得从数字密集摘要伪造行列。
5. 每张恢复表写 `recovered_tables.jsonl`；每行写 `recovered_table_rows.jsonl`。必须保留：

```text
run_id
source_id
raw_asset_id
parsed_table_id 或 recovered_table_id
table_row_id
storage_path
source_url
checksum
source_location（到 table/row/column）
caption
footnotes
columns_json
cells_json
row_text
row_hash
```

6. 表格去重键为 `canonical raw checksum + table hash + row hash`；OpenFDA/DailyMed 重复标签、PMC 压缩包内文件与独立下载文件只保留 canonical 行，别名写入状态记录。
7. 确定性表格抽取只接受以下情况：
   - 旧 `parsed_table` 的列数必须与每行单元格数一致，列名不能是脚注或超长正文；不满足时不得复用其列语义，必须回 raw 重建或进入审核队列；
   - SPL 首行 `colspan` 表题与下一行真实列名必须分开；`tfoot` 和脚注不得作为列名或数据行；
   - 位于 `tbody` 但通过 `colspan` 横跨全表的重复说明/脚注行也不得抽 evidence；
   - 参数、数值和单位能由明确列名或同一完整行一一对应；
   - 一个数值单元格只能含一个中心估计值；`均值 ± 标准差` 算一个估计值，多组均值挤在同一单元格时不得自动拆分；
   - 参数与单位维度兼容；
   - 化合物由表格行、表题/表头、DailyMed 唯一活性成分或 OSP 精确目录名确定；
   - DailyMed/OpenFDA 复方标签不能仅因表题出现目标药名而归属；只有唯一活性成分标签可确定性写 evidence；
   - DDI 表中的受害药、施害药和参数方向必须人工或表格专用 LLM 判断，确定性阶段不直接写数值 evidence；
   - `creatinine clearance`、`CL cr`、`CrCl`、`eGFR` 是受试者肾功能条件，不是目标药物 clearance 参数；
   - 所有 PDF 表（包括旧 `parsed_table` 和本阶段坐标恢复表）都可能把小数或置信区间跨单元格切断，确定性阶段只保留表和行，不直接写 evidence；必须经表格专用 LLM 或人工核对页面图像后再进入 evidence；
   - 比较组、剂量、给药途径和人群能保留为 condition，不把它们误当参数值。
8. 不能确定列语义、化合物归属、比较方向或单位的完整行写 `table_review_queue.jsonl`，不直接写 evidence。
9. 只有带完整 caption、列名、完整行、脚注和可靠 `source_location` 的 review row 才可在独立表格 LLM 任务中辅助解释；LLM 不接收整份文件、整张大表或展平 chunk，不能补写原表没有的数值。
10. 表格 evidence 写 `table_evidence_candidates.jsonl`，并在去重后合并进 `evidence_candidates.jsonl`；全部保持 `machine_extracted + needs_review`。
    - 对 `compound + parameter + canonical value/unit + 规范化完整行 + 规范化 condition` 计算科学内容指纹；
    - 同一科学行在多个标签版本或 OpenFDA/DailyMed 镜像中重复时，优先保留 DailyMed，再按稳定 source location 选 canonical；
    - 被合并的记录写 `table_evidence_duplicates.jsonl`，保留 duplicate evidence ID、canonical evidence ID 及双方完整来源，不能直接删除溯源；
    - 同值但不同完整行或不同 condition 不得合并。

### 5. Step 2：化合物归属

#### 5.1 身份表

身份表至少包含：

```text
preferred_name
PubChem CID / synonyms / InChIKey
RxNorm names / RxCUI
ChEMBL ID 和 exact molecule identity
UNII
DailyMed / FDA active ingredient names
盐型、前药、代谢物、立体异构体关系
```

related form 只能记录关系，不自动合并为母体化合物。

#### 5.2 规则归属

每条 candidate 使用：

```text
source_text
source title
section title
source metadata
retrieval compound
source_id
evidence_type
parameter
```

角色只能是：

```text
target_compound
victim_drug
perpetrator_drug
co_medication
comparator
excipient
mentioned_only
shared_or_unlinked
```

执行顺序：

1. 先做同义词、稳定 ID 和活性成分精确匹配。
2. 再结合来源和章节判断，例如 Clinical Pharmacology、Drug Interactions、Specific Populations。
3. `A increased B AUC`：A 通常是 perpetrator，B 是 victim。
4. `B was inhibited by A`：B 是 victim，A 才可能是 perpetrator。
5. probe/cocktail 只承认局部药物-酶/转运体配对；多药多靶点且无法局部对齐时不得归属。
6. comparator、excipient、mentioned_only 和无法解释的 co-medication 不进入最终证据层。
7. PubChem 结构化属性可在 exact retrieval identity 下归属；ChEMBL 搜索结果必须再证明 exact molecule identity。
8. OSP 模型只在文件名、模型 metadata 或报告明确匹配目标化合物时归属；共享仓库快照不能绑定给所有化合物。
9. DailyMed/OpenFDA 的表格行或章节未重复药名时，仅当活性成分字段证明该文档是单一目标药物制剂，才能使用文档级身份归属；复方制剂不得自动继承检索化合物。
10. 普通 PK 句子仅出现 `AUC`、`Cmax`、`exposure`、`clearance` 不构成 DDI。只有 evidence 类型已是 DDI，或文本同时存在多药关系与相互作用动作，才进入 victim/perpetrator 判定。
11. `target is a probe/sensitive substrate`、`effect of A on target PK`、`target AUC/Cmax increased or decreased by A` 可高置信归属为 victim；`target inhibits/induces enzyme or another drug` 可高置信归属为 perpetrator。

#### 5.3 LLM 归属复核

仅以下情况调用 LLM：

```text
同一 source_text 出现两个以上药物
DDI victim/perpetrator 无法由规则确定
coadministered / concomitant / versus / compared with 等多药关系
probe/cocktail 多药多靶点无法局部配对
section 与 source_text 指向不一致
ChEMBL exact identity 无法证明
规则置信度 < 0.80
长段落包含多个剂量、人群、药物或研究组
```

LLM 只能输出：

```text
evidence_id
matched_text
compound_name
compound_role
role_reason
confidence
```

`matched_text` 必须逐字存在于 `source_text`，`compound_name` 必须命中身份表。LLM 不能改写原文、生成新 evidence 或改变 `curation_status`。

若 `source_text` 中没有身份表内的药名或同义词，且不存在单活性成分文档级身份，LLM 不得猜测归属；该记录保留为 `shared_or_unlinked`。

### 6. Step 3：领域质量门控

领域门控必须在任何 embedding 之前执行。被排除记录保留完整来源和 `exclusion_reason`。

#### 6.1 Physicochemical

只允许纯化合物结构和理化属性：

```text
MolecularFormula, MolecularWeight, InChIKey, CanonicalSMILES,
XLogP/LogP/LogD, TPSA, pKa, solubility, ionization,
fraction_unbound, protein_binding, hydrogen-bond donor/acceptor count
```

排除 dose、formulation、product strength、食品/植物/样本含量和制剂描述。

#### 6.2 ADME

只允许目标化合物自身的 absorption、distribution、metabolism、excretion、bioavailability、permeability、protein binding、enzyme/transporter mechanism 和 metabolite formation。

排除药效学、受体/细胞信号、行为终点、植物合成和“目标药影响其他对象 ADME”但不是目标药自身 ADME 的句子。

#### 6.3 Clinical PK

只允许明确 PK 参数或暴露结论，例如 AUC、Cmax、Tmax、half-life、clearance、volume of distribution、bioavailability、fraction excreted 和 concentration。

dose、route 和 formulation 只能作为条件字段；疗效、安全性、生理或运动终点不得作为 Clinical PK evidence。

#### 6.4 DDI

必须能确定 victim、perpetrator/interacting drug、effect/mechanism 和 direction。probe substrate 身份、cocktail 共现、复方标签共现和方向不明的多药句子不构成 DDI。

无法确定方向的表格和文本进入隔离队列，由专用关系抽取 LLM 复核；仍无法确定时不进入 semantic dedup 输入。

领域门控输出状态固定为 `passed`、`needs_manual_review`、`excluded`。`needs_manual_review` 保存在 `domain_review_queue.jsonl`，不会被误写成门控通过。

#### 6.5 Special Population

必须明确 population/condition，例如 pregnancy、lactation、pediatric、geriatric、renal/hepatic impairment、genotype 或 sex difference。动物研究必须显式记录 species，不与人体 PK 混合。

#### 6.6 Public PBPK Model

分为：

```text
downloadable_public_model
published_pbpk_model
model_mention_only
```

只有前两类可进入 reviewable；OSP 模型必须有模型、参数、脚本或评价报告路径。普通 population PK/PD 或只出现 “model” 的文本排除。

#### 6.7 Tissue Expression

当前输入为 0 条，必须如实报告缺口。不得从普通 enzyme/transporter 提及伪造 tissue-expression evidence。

### 7. Step 4：确定性去重

去重只建组，不删除 candidate。按顺序执行：

1. `evidence_id` 重复。
2. `raw_asset_id + source_location + source_text_hash` 来源重复。
3. `compound + evidence_type + parameter + canonical_value/value + canonical_unit/unit + condition + source_text_hash` 内容重复。

每组保留全部 member，并选择一个 deterministic representative。代表优先级：

```text
provenance 完整
compound attribution 高置信
数值/单位/条件完整
canonical value/unit 完整
来源优先级更高
source_location 更精确
extraction_confidence 更高
```

DailyMed 与 OpenFDA 同一 SPL、PMC 包内文件与独立下载、同一段落多次切块必须在本步骤合并成组。

对 `source_structured_table`、`parsed_table_id` 或 recovered-table 记录，如果 compound、evidence_type、parameter、canonical value/value、canonical unit/unit 和 `source_text_hash` 相同，则视为同一表格事实；不同标签对 condition 的格式化或产品名称写法差异不能阻止确定性去重。所有 member 的原 condition 仍保留用于审计。

完成三层去重后，未被折叠的最终代表写入 `deterministic_representatives.jsonl`；其中通过领域门控、归属角色有效且属于自然语言的记录另写入 `semantic_dedup_input.jsonl`，作为 Step 5 的唯一输入。

### 8. Step 5：evidence 语义去重 embedding

#### 8.1 输入范围

仅处理同时满足以下条件的记录：

```text
provenance 已通过
compound attribution 已明确
领域门控已通过
已是确定性重复组代表
source_text 是自然语言
```

结构化 ID/数值字段、表格单元格重复、被排除记录和 table review queue 不送 embedding。

#### 8.2 模型与输入

```text
model = NeuML/pubmedbert-base-embeddings
runtime = sentence-transformers
dimension = 768
```

输入文本由以下字段稳定拼接：

```text
compound
evidence_type
parameter
value_text
condition
population
source_text
```

只在同一 compound、同一 evidence_type 内比较；参数明确时进一步限制在同一 parameter 组。

#### 8.3 判定

```text
similarity >= 0.92             duplicate candidate
0.85 <= similarity < 0.92      similar_for_review
similarity < 0.85               不分组
```

`semantic_duplicate` 自动重复组必须满足组内任意两条 evidence 的 cosine similarity 均不低于 `0.92`。仅与某一中心 evidence 达到 `0.92`、但组内存在低于 `0.92` 的成员对时，不自动合并，整组降级为 `similar_for_review`。

高相似但数值、单位、剂量、途径、人群或条件冲突时不得合并，直接交给冲突分析。embedding 只发现相似文本，不能生成、修正或裁决科学事实。

`semantic_duplicate_groups.jsonl` 中必须用 `semantic_duplicate`、`similar_for_review`、`semantic_conflict_candidate` 明确区分三类结果；`semantic_duplicate_members.jsonl` 的每一行也必须保留 `group_type`；冲突候选同时写入 `semantic_conflict_candidates.jsonl`。

禁止使用 `hashing-embedding-v0` 作为最终 evidence 去重 fallback。GPU 或模型不可用时只能记录明确 blocker，不能把步骤标记完成。

### 9. Step 6：冲突分析

输入固定为 `deterministic_representatives.jsonl`、语义去重 group/member 文件和领域门控结果。先移除 `semantic_duplicate` 的非代表成员；`similar_for_review` 与 `semantic_conflict_candidate` 成员不得自动删除。

冲突候选 key：

```text
compound
evidence_type
parameter
canonical_unit
route
population
condition
```

比较 value、unit、dose、route、population、condition、label version 和 study design。

执行规则：

1. 每个 `semantic_conflict_candidate` 必须生成一条冲突分析记录，所有成员在 `conflict_members.jsonl` 中且只能映射到一个语义冲突分析组。
2. 对尚未进入语义冲突组的代表 evidence，再按上述冲突 key 扫描结构化数值或方向结论冲突。
3. 只有组内独立结构化的 route、population、dose、time point、study design 或 label version 存在明确非空差异时，才能标记 `explainable_variation`。condition 中识别出的 fed/fasted、肾/肝功能、妊娠/哺乳、年龄、性别、吸烟或基因型标签只作为审核提示；仅自由文本 condition 不同必须标记 `insufficient_context`。
4. 同条件或条件缺失时，canonical 数值区间不重叠、同单位数值不一致、或 increase/decrease/no-effect 方向不一致，标记 `unresolved_conflict`。
5. 单位无法比较、条件部分缺失或文本同时含多种方向时，标记 `insufficient_context`，自动排除出默认 reviewable。
6. 数值区间重叠、数值在 1% 相对容差内一致或方向一致时，标记 `compatible`。来自 `semantic_conflict_candidate` 的 compatible 组仍需人工确认是否为重复表述，不得直接进入 reviewable。

剂量、给药途径、人群、时间点、研究设计或标签版本不同且能解释差异时，保留为不同条件 evidence，不标记真正冲突。条件相同或缺失且结论/数值不一致时写入 conflict group，并自动排除出默认最终证据层。

冲突分析不能平均数值、选择“看起来合理”的数值或让 LLM 裁决真伪。

### 10. Step 7：证据分层与自动验证

| 层 | 定义 | 默认用途 |
|---|---|---|
| `candidate` | 7,330 条不可变机器候选 | 审计、debug |
| `excluded` | provenance、归属或领域门控未通过，保留原因 | 质量审计 |
| `preselected` | 归属明确、领域门控通过、去重后的代表 evidence | 冲突与自动质量验证 |
| `reviewable` | preselected 中不存在未解决归属、表格、相似或冲突 blocker 的 evidence | 默认 UI、搜索、Q&A、Agent |
| `accepted` | 可选人工覆盖层；自动流程不依赖 | 兼容旧审核接口 |
| `modeling` | 可选人工覆盖层；自动流程不依赖 | 兼容旧建模审批接口 |

文件层生成规则：

1. `preselected` = 领域门控通过的 deterministic representative，减去 `semantic_duplicate` 非代表成员；冲突和相似待复核成员仍保留并附 blocker。
2. `reviewable` = `preselected` 中没有 `similar_for_review`、semantic-conflict `compatible` duplicate review、`unresolved_conflict`、`insufficient_context` 或其他未解决 blocker 的记录。
3. `excluded_from_reviewable` 与 `reviewable` 必须按 `evidence_id` 完整分割 7,330 条 candidate，并为每条被排除记录保存 `exclusion_reasons`。
4. 自动流水线以 `reviewable` 作为 blocker-free 最终证据层。`accepted_evidence.jsonl` 和 `modeling_evidence.jsonl` 仅兼容可选人工覆盖，没有 curation event 时保持为空。

旧 `curation_status=needs_review` 只表示没有人工事件，不再阻塞自动知识库和推荐流程；自动可用性由 evidence layer、provenance、领域门控、去重和冲突状态共同决定。

`table_review_queue.jsonl` 仍是独立隔离队列。表格专用 LLM 重新解析后产生的新 candidate 必须从 Step 1 重新进入本流水线，不能直接追加到 reviewable；无法自动解决的条目保持排除状态。

### 11. Step 8：后置 RAG 检索索引

只有 `reviewable_evidence.jsonl` 已完成后才执行。

检索索引采用高相关性白名单，不全量索引 raw processing 中的全部 chunk 和表格。输入按以下顺序生成：

```text
reviewable_evidence.source_text
accepted_evidence.source_text
reviewable/accepted 精确引用的 text_chunks.chunk_text
与引用 chunk 位于同一 parsed document、同一来源位置前缀且 chunk_index 相邻 +/-1 的上下文
reviewable/accepted 精确引用的可靠 parsed/recovered table_text
```

实现规则：

1. 不引用最终 evidence 的普通 raw chunk、普通表格和 table review queue 不进入 Stage 1 默认 RAG 索引。
2. 相邻上下文必须同时满足同一 `parsed_document_id`、同一去除 `#chunk=` 后的 `source_location` 前缀和相邻 `chunk_index`，防止跨文章或跨标签章节串入。
3. 表格仅按 `parsed_table_id`/`recovered_table_id` 精确关联。`parsed_tables.table_text` 直接使用；结构可靠但没有 `parsed_table_id` 的 recovered table，按已保存的 caption、`columns_json` 和按 `row_index` 排序的 `recovered_table_rows.row_text` 确定性重建表文本。缺行或结构不可靠时只保留对应 evidence 原文，不拼造表格内容。
4. 对 `(compound_id, source_location, normalized_text_hash)` 做检索记录去重；合并记录类型和关联 evidence ID，不丢失来源。
5. 每条检索记录保存 `retrieval_record_id`、`compound_id`、`source_id`、`source_location`、`source_text`、`source_text_hash`、`evidence_layer`、关联 evidence/chunk/table ID 和完整 provenance。
6. `source_text` 始终保存原文。向量输入另存为 `embedding_text`，由化合物名、证据类型、参数名、值/单位和原文确定性拼接；对于只有 `194.19` 等短字段值的结构化 evidence，不允许只嵌入孤立数值，也不得用 LLM 改写原文。
7. 使用 `NeuML/pubmedbert-base-embeddings` 生成 768 维归一化向量；GPU/模型不可用时该步骤保持失败或未完成，不得回退到 hash embedding。
8. 文件输出固定为 `06_rag_index/retrieval_records.jsonl`、`retrieval_embeddings.npy` 和 `rag_index_summary.json`，记录行与向量行按 `embedding_row` 一一对应。

检索 embedding 与 Step 5 的语义去重 embedding 是两个独立任务：

- 去重 embedding 只比较 evidence，输出 duplicate/similar group。
- RAG embedding 服务 Evidence Search、Q&A 和 Agent，输出 retrieval index。
- 两者必须分目录、分 stage、分 summary；不得因为模型相同就混用状态或输出。
- 检索命中必须返回 `source_id`、`source_location`、`source_text` 和 evidence layer。

### 12. Step 9：数据库、UI、Q&A 和导出

1. 只导入本次 7,330 条 candidate 及其精确关联的 raw/parsed 文档，不把 raw processing 中未被最终 evidence/RAG 引用的普通文档全量灌入 Stage 1 运行数据库。
2. candidate、excluded、preselected、reviewable、accepted、modeling 使用 `evidence_layer_membership` 分层入库；数据库 view 读取本次文件分层，不再用另一套 SQL 规则重新推导 reviewable。
3. deterministic/semantic duplicate group 和 conflict group/member 分别入库，保留 representative、状态、原因、相似度和自动排除原因。
4. RAG 使用独立 `rag_retrieval_record` 表和 `vector(768)` 字段，导入 `retrieval_records.jsonl` 与 `retrieval_embeddings.npy`；禁止写入旧 1536 维 hash `document_chunk.embedding`。
5. Compound Profile、Evidence Search、Source Registry、Q&A、KG、导出和推荐 Agent
   只读取 `07_llm_quality_validation/final_auto_validated_evidence.jsonl` 对应的
   `auto_validated_evidence` 数据库服务层；reviewable、repair_pending、quarantined、
   duplicate member、superseded 和 unresolved evidence 不进入默认检索。
6. 可选人工动作仍必须写 `curation_event`，但统一自动流水线不等待人工动作。
7. Q&A 和 Agent 必须显示 evidence layer、自动验证结果、来源和不确定性，不得把 reviewable 描述成人工确认。
8. 自动导出默认 auto_validated；所有导出保留 evidence layer、质量状态和 provenance。
9. Evidence Gap 按来源职责和最终 auto_validated 覆盖计算；不得直接使用 raw
   completeness 中全部 `missing_from_raw` 行。

### 13. 验收标准

```text
input_candidate_count = 7330
missing_provenance_count = 0（进入 preselected/reviewable 的记录）
unresolved_compound_attribution_count = 0（进入 preselected/reviewable 的记录）
domain_gate_result_count = 7330
every duplicate member resolves to one duplicate group
semantic dedup uses NeuML/pubmedbert-base-embeddings
every conflict member resolves to one conflict group
every excluded candidate has exclusion_reason
every reviewable evidence has source_text and source_location
every accepted/modeling evidence has curation_event
reviewable_count + excluded_from_reviewable_count = 7330
semantic duplicate non-representatives are absent from preselected/reviewable
similar_for_review and unresolved/insufficient conflict members are absent from reviewable
reviewable contains no repeated structured-table fact with the same compound/type/parameter/value/unit/source_text_hash

```

### 14. 禁止项

- 不得使用旧 run 或旧 final evidence 结果混入本次运行。
- 不得在归属、领域门控和确定性去重之前运行 evidence embedding。
- 不得把 RAG 检索 embedding 当作语义去重结果。
- 不得删除 candidate 来解决重复或冲突。
- 不得把 LLM 总结当作原文。
- 不得把 `needs_review` 当作人工确认。
- 不得把 comparator、excipient、mentioned_only 当作目标证据。
- 不得把 dose、formulation、食品/样本含量当作纯化合物理化性质。
- 不得把药效学、行为或安全性终点当作 ADME/Clinical PK。
- 不得把 probe/cocktail 共现当作 DDI。
- 不得自动合并数值或条件冲突。
- 不得把 table review queue 直接写入最终 evidence。
- 不得导出没有 provenance 的 evidence。

### 15. 统一执行入口

`python -m pbpk_kb.main` 在原始资料处理完整性验收通过后固定调用：

```text
  -> domain_and_deterministic_dedup
  -> semantic_dedup
  -> conflict_and_evidence_layers

  -> deterministic_quality_control
  -> llm_quality_validation

```

`semantic_dedup` 只能读取确定性去重生成的 `semantic_dedup_input.jsonl`；`rag_index`
只能在 `reviewable_evidence.jsonl` 完成后生成候选检索记录；`database_import` 必须等
`final_auto_validated_evidence.jsonl` 和最终质量 summary 完成后，再过滤并写入服务层。
统一 manifest 和各阶段 `pipeline_state.json` 同时记录状态，失败后再次运行主函数只续跑
未验收阶段，不重复覆盖已验收输出。


## 自动证据质量控制策略

### 1. 目标

将 `reviewable_evidence.jsonl` 中的机器候选分为：

```text
auto_validated：可进入数据库、KG、检索和推荐计算
repair_pending：可从原文、表格或相邻上下文补读后再次验证
quarantined：证据保留，但不得进入 KG 或推荐计算
```

不设置人工审核为必经步骤，不推断原文没有提供的值、单位、药物、对照组或实验条件。

### 2. 输入和输出

输入：

```text
05_evidence_layers/reviewable_evidence.jsonl
04_conflict_analysis/evidence_conflict_report.jsonl
04_conflict_analysis/conflict_members.jsonl
原始文件、parsed document、parsed table、相邻 text chunk
```

输出：

```text
06_auto_quality_control/quality_decisions.jsonl
06_auto_quality_control/auto_validated_evidence.jsonl
06_auto_quality_control/repair_pending_evidence.jsonl
06_auto_quality_control/quarantined_evidence.jsonl
06_auto_quality_control/context_repair_requests.jsonl
06_auto_quality_control/kg_ready_nodes.jsonl
06_auto_quality_control/kg_ready_edges.jsonl
06_auto_quality_control/quality_summary.json
07_llm_quality_validation/final_auto_validated_evidence.jsonl
07_llm_quality_validation/final_quarantined_evidence.jsonl
07_llm_quality_validation/final_quality_decisions.jsonl
07_llm_quality_validation/quality_summary.json
```

### 3. 固定执行顺序

#### Step 1：来源和原文校验

每条 evidence 必须具备：

```text
evidence_id
compound_id
source_id
raw_asset_id
storage_path
checksum
source_location
source_text
source_text_hash
extraction_method
extractor_version
```

重新计算 `source_text_hash`。原文为空、hash 不一致、文件不存在或来源定位缺失时直接 `quarantined`。

#### Step 2：字段类型和领域校验

检查 evidence type、compound role、parameter、数值类型和领域边界。

```text
physicochemical：结构或理化属性
adme：吸收、分布、代谢、排泄、酶和转运体机制
clinical_pk：AUC、Cmax、Tmax、半衰期、清除率、分布容积等
ddi：两个药物之间的暴露变化或明确机制
special_population：特定人群中的 PK/ADME 差异
tissue_expression：组织中的酶或转运体表达
public_pbpk_model：明确的 PBPK 模型资料
```

比较药、辅料、仅提及药物和未归属记录不得通过。

#### Step 3：缺失值和单位处理

1. 定性 ADME、机制关系和模型描述允许 `value=null`、`unit=null`。
2. 定量参数有数值时必须有单位；无量纲 ratio/fold 除外。
3. 从 `source_text` 中只接受唯一且紧邻参数数值的单位。
4. 使用 `unit_normalizer.py` 生成 `canonical_value` 和 `canonical_unit`。
5. 单位维度必须和参数匹配，例如 Cmax 使用浓度、AUC 使用浓度乘时间、半衰期使用时间。
6. 原文无法唯一确定单位时生成 `context_repair_request`，不得猜测。
7. 文本声称定量结果但没有可抽取数值时生成修复请求。

#### Step 4：上下文和参照对象校验

`clinical_pk` 定量记录检查 dose、route、population 和 condition；缺失字段不必全部阻断，但写入 `context_missing_fields`。

下列记录必须存在参照对象或基线：

```text
increase/decrease/change/difference
ratio/fold/percent change
DDI 暴露变化
特殊人群相对健康人群的变化
```

参照对象可以来自结构化字段、condition、source_text 或可追溯相邻上下文。无法确定时进入 `repair_pending`。

DDI 必须明确：

```text
victim drug
perpetrator drug 或明确酶/转运体机制
作用方向或量化影响
```

只有目标药物自身普通 PK 数值的记录不得作为 DDI。

#### Step 5：确定性修复

只执行以下可证明的修复：

```text
从同一原文中恢复唯一单位
规范化单位和数值
从明确字段恢复 route、dose、population、reference
合并同一表格行的表头、脚注和单元格上下文
从相邻 chunk 恢复被截断的完整句子
```

每项修复保存：

```text
field
old_value
new_value
supporting_text
supporting_location
repair_method
```

#### Step 6：LLM 精确抽取

仅对 `repair_pending` 调用 LLM。输入限于原 evidence、原文所在段落、表格表头/脚注和相邻 chunk。

LLM 只能返回原文支持的字段和逐字引用，不能使用外部知识。返回值必须再次通过 Step 1 至 Step 4。

#### Step 7：独立 LLM 验证

使用独立请求重新读取原文和修复结果，输出：

```text
supported
unsupported_fields
compound_role_correct
parameter_value_unit_correct
reference_correct
context_sufficient
verbatim_support
confidence
```

抽取请求和验证请求不得共享先前的解释文本。验证失败时最多回读修复一次；仍失败则 `quarantined`。

#### Step 8：冲突校验

以 compound、parameter、canonical unit、dose、route、population、condition、study design 和时间点分组。

```text
条件不同：保留为 context-specific evidence
条件相同且数值兼容：保留来源独立的支持关系
条件相同且数值或方向冲突：全部隔离，不平均、不自动选真值
条件缺失导致无法比较：进入 repair_pending
```

#### Step 9：自动准入

只有同时满足以下条件才标记 `auto_validated`：

```text
来源和逐字原文完整
化合物归属和角色明确
领域分类正确
参数、数值、单位不存在类型冲突
定量证据的单位可解释
相对变化的参照对象明确
DDI 双方角色或机制明确
不存在未解决冲突
不存在阻断型缺失字段
规则校验通过
LLM 参与修复时独立 LLM 验证通过
```

### 4. KG 输出约束

KG 只读取 `auto_validated_evidence.jsonl`。

节点：

```text
Compound, Parameter, Enzyme, Transporter, Population, Tissue,
PublicModel, StudyContext, SourceDocument, Evidence
```

边：

```text
HAS_EVIDENCE, HAS_PARAMETER, SUBSTRATE_OF, INHIBITS, INDUCES,
TRANSPORTED_BY, HAS_DDI_WITH, STUDIED_IN, EXPRESSED_IN,
DESCRIBED_BY_MODEL, SUPPORTED_BY, CONFLICTS_WITH
```

每条事实边必须携带：

```text
evidence_id
source_id
source_location
source_text_hash
quality_status=auto_validated
validation_method
confidence
```

`repair_pending` 和 `quarantined` 只可作为审计节点，不得生成科学事实边。

### 5. 最终数据库与 UI 服务层

数据库导入必须在 LLM 修复和独立验证完成后执行，固定读取：

```text
07_llm_quality_validation/final_auto_validated_evidence.jsonl
```

分层规则：

```text
final_auto_validated -> auto_validated_evidence 数据库视图
final_quarantined -> 只保留文件和审计记录
reviewable/repair_pending -> 只保留过程审计
candidate/preselected/excluded -> 只保留过程审计
```

Compound Profile、Evidence Search、Source Registry、Q&A、KG、导出和推荐只读取
`auto_validated_evidence`。`reviewable_evidence` 不得作为最终服务层。

导入器必须：

1. 校验最终文件行数等于最终 `quality_summary.json` 的
   `final_auto_validated_count`。
2. 校验每条记录的 evidence ID、化合物归属、来源、原文、checksum 和 provenance。
3. 使用最终修复字段覆盖候选表旧字段，状态写为 `auto_validated`。
4. 只为最终通过 evidence 重建理化、ADME、Clinical PK、DDI 和特殊人群服务表。
5. 只导入关联最终通过 evidence 或其可追溯 chunk 的 RAG 记录。
6. 隔离和过程层不得被 UI、API、KG、Q&A、导出或推荐查询返回。
